# PLAYPORT 로그인 및 주문 저장

JSP / Jakarta Servlet / PostgreSQL을 사용하는 Maven WAR 프로젝트입니다.
Java 21과 Tomcat 10.1을 기준으로 합니다. 현재 Servlet API 및 web.xml 버전은 6.0입니다.

## 실행 준비

1. 기존 게임 DB에서 `sql/006_create_users.sql`을 한 번 실행합니다.
   예: `psql -U your_database_user -d gamestore -f sql/006_create_users.sql`
   이어서 `sql/007_add_order_user.sql`을 한 번 실행하여 orders에 회원 ID를 연결합니다.
   기존 주문이 있다면 소유자를 먼저 연결해야 하며, 이번 로컬 DB에는 빈 주문 테이블에 적용했습니다.
   관리자·게임 등록에는 `sql/008_add_user_role.sql`을 실행하고,
   표지가 포함된 샘플 게임 3개를 추가하려면 `sql/010_seed_games.sql`을 실행합니다.
   008·010은 이번 로컬 DB에 이미 적용했습니다. 실제 관리자 승격은 아래 009 SQL로 직접 선택하세요.
   게임 정보 수정·판매 중지에는 `sql/012_add_game_sale_status.sql`도 배포 전에 실행합니다.
   현재 로컬 DB에는 012까지 적용했으며 기존 게임은 모두 판매 중 상태입니다.
   주문 중복 방지와 찜 목록에는 `014_order_checkout_tokens.sql`, `015_create_wishlist.sql`을 배포 전에 적용합니다.
   현재 로컬 DB에는 이 두 파일도 적용했습니다. 기존 주문은 그대로 유지됩니다.
   주문 상태·테스트 결제·취소에는 `016_order_status.sql`도 배포 전에 적용합니다.
   현재 로컬 DB에는 016도 적용했고 기존 주문 4건은 완료 상태로 보존했습니다.
   리뷰·별점에는 `017_create_reviews.sql`을 배포 전에 적용합니다. 현재 로컬 DB에는 이미 적용했습니다.
   상세 정보·갤러리에는 `018_game_details.sql`이 필요합니다. `019_seed_game_details.sql`은 가상의 Moonlit 샘플 정보·이미지 2장을 추가합니다.
   현재 로컬 DB에는 두 파일 모두 적용했고 기존 게임 가격·계정·주문·찜·리뷰는 보존했습니다.
   `020_seed_catalog_metadata.sql`도 적용하여 기존 12개 가상 게임의 개발사·출시일·지원 언어를 모두 채웠습니다. 이미지·갤러리는 변경하지 않습니다.
2. 기존 `db.properties`의 `db.url`, `db.user`, `db.password`를 확인합니다.
   파일 형식은 `db.properties.example`을 참고하세요.
3. Tomcat 실행 환경에 `GAMESTORE_DB_CONFIG`를 db.properties의 절대 경로로 지정합니다.
   예: PowerShell에서 `$env:GAMESTORE_DB_CONFIG = 'C:\Working\gamestore\gamestore\db.properties'`
   환경 변수를 설정한 터미널에서 Tomcat을 실행해야 적용됩니다.
   IDE 또는 Windows 서비스로 실행한다면 해당 실행 환경에 설정하고 재시작하세요.
   미설정 시 기존처럼 프로세스 작업 폴더의 `db.properties`를 읽습니다.
   비밀번호가 들어 있는 설정 파일은 WAR나 소스 저장소에 추가하지 마세요.
4. 프로젝트 폴더에서 아래 재배포 명령을 실행합니다. 테스트·WAR 생성·Tomcat 복사를 한 번에 처리합니다.
5. `/gamestore/register`에서 가입한 뒤 `/gamestore/login`으로 로그인합니다.

## 재배포 명령

프로젝트 폴더(`C:\Working\gamestore\gamestore`)에서 실행하세요.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\deploy.ps1
```

이 스크립트는 기존 WAR가 없어도 새로 빌드합니다.
배포용 WAR는 `.artifacts/gamestore.war`에 생성하므로 `target` 정리와 분리됩니다.
일반 `mvn package`의 기본 출력 위치는 여전히 `target/gamestore.war`입니다.
빌드가 실패하면 기존 Tomcat WAR를 교체하지 않습니다.
복사는 임시 파일에서 SHA-256을 확인한 뒤 완료된 WAR를 교체합니다.
Tomcat 실행·재시작은 하지 않으며, 실행 중인 Tomcat의 자동 배포가 끝난 뒤 브라우저를 새로고침하세요.
Tomcat을 꺼 둔 상태라면 복사 후 기존 방식대로 실행하세요.

기본 Tomcat 위치는 현재 Windows 사용자 폴더의 `scoop/apps/tomcat10/current`입니다.
다른 설치 위치는 `-TomcatHome 'D:\Servers\tomcat'`으로 지정할 수 있습니다.
이미 테스트한 변경을 빠르게 배포하려면 끝에 `-SkipTests`를 붙일 수 있습니다.
이 명령의 ExecutionPolicy 설정은 해당 PowerShell 실행에만 적용됩니다.

WAR 출력 설정 참고: https://maven.apache.org/components/plugins-archives/maven-war-plugin-3.4.0/war-mojo.html#outputDirectory

## 현재 상태 백업

프로젝트 폴더에서 `powershell -NoProfile -ExecutionPolicy Bypass -File .\backup.ps1`을 실행합니다.
저장소 루트의 `backups/`에 날짜별 새 폴더를 만들며 현재 소스·이미지·Git 기록,
배포된 WAR·Tomcat 설정·DB 접속 설정과 PostgreSQL 전체 덤프를 보관합니다.
프로젝트 ZIP의 모든 파일 해시와 별도 임시 DB로 실제 복원한 모든 테이블의 내용을 검증합니다.
백업은 로컬 사용자·SYSTEM·관리자만 접근할 수 있고 Git에서 제외합니다.
복구 절차와 백업 구성은 `docs/backup-restore.md`에 있습니다.

## 인디 게임숍 UI

크림색 바탕과 살구·세이지 색상을 사용하는 공통 테마를 적용했습니다.
홈(`/gamestore/home`)은 최근 등록한 게임 배너와 신착·인기·고평점 섹션, 전체 게임 목록 링크로 구성됩니다.
각 섹션은 판매 중인 게임을 최대 4개씩 표시하며 고정 표지 우선 추천 대신 실제 등록·완료 주문·리뷰 데이터를 사용합니다.
게임 목록(`/gamestore/browse`)에서 제목·장르 검색, 장르 필터와 정렬을 함께 사용할 수 있습니다.
예: `/gamestore/browse?q=moon&genre=Simulation&sort=price_asc`.
한 페이지는 9개이며 `page=2`로 다음 페이지를 요청할 수 있습니다.
DB에서 검색·필터·정렬·개수 계산 후 LIMIT/OFFSET으로 해당 페이지의 상품만 가져옵니다.
개수·상품·장르 목록은 같은 읽기 스냅샷에서 조회합니다.
페이지 링크는 검색어·장르·정렬을 유지하고, 검색·장르·정렬을 바꾸면 첫 페이지부터 표시합니다.
잘못된 페이지 값은 첫 페이지로, 전체 범위를 넘는 양의 페이지 번호는 마지막 페이지로 맞춥니다.
정렬 값은 `added`(ID 기준 최신 추가순, 기본값), `price_asc`(낮은 가격),
`price_desc`(높은 가격), `title`(제목순)입니다. 같은 가격은 ID가 큰 게임부터 표시합니다.
장르를 바꾸거나 검색·정렬을 적용해도 다른 선택 조건은 URL에 유지됩니다.
이전 `/home?q=...&genre=...` 검색 주소는 조건을 보존하여 새 목록으로 이동합니다.
상단 홈·게임 목록 메뉴를 구분했고, 카트·주문 완료·상세에서 쇼핑을 계속하면 게임 목록으로 이동합니다.
검색 결과가 없을 때는 조건을 지울 수 있는 빈 상태 화면을 보여줍니다.

공통 JSP 조각은 `WEB-INF/jspf/head.jspf`, `header.jspf`, `footer.jspf`, `game-card.jspf`입니다.
각 JSP 조각에 UTF-8을 명시했고, 금액은 JSTL로 천 단위 구분자를 표시합니다.
스타일은 `css/style.css`의 `:root` 색상 변수와 반응형 규칙에서 관리합니다.
별도 CSS 프레임워크나 외부 폰트 다운로드 없이 동작합니다.
관리자 화면의 표지 선택에는 `js/store.js`의 이미지 미리보기를 연결했습니다.

게임 상세는 기존 DB의 `description`을 읽어 내용이 있을 때 설명 섹션을 표시합니다.
관리자 게임 등록에는 선택 입력인 게임 설명(최대 5,000자)을 함께 저장합니다.
등록된 게임은 관리자 목록의 `説明を編集`에서 설명을 추가·수정할 수 있습니다.
설명 편집 주소는 `/gamestore/admin/games/description?id=게임ID`입니다.
설명만 갱신하므로 제목·가격·장르·이미지는 유지됩니다.
일본어와 줄바꿈을 유지하며 HTML은 실행하지 않고 문자 그대로 표시합니다.
빈 설명을 저장하면 상세 페이지의 설명 영역이 사라집니다.
입력 검증 또는 저장 실패 시 작성한 내용을 유지합니다. 기존 DB에 description TEXT가 있어 추가 SQL은 필요하지 않습니다.

현재 데모 게임 6개의 일본어 소개는 표지와 장르에 맞춰 작성한 가상 게임 소개입니다.
`sql/011_seed_game_descriptions.sql`에 보관했으며 현재 로컬 DB에는 적용했습니다.
이 SQL은 제목·이미지가 일치하고 설명이 비어 있는 게임만 채우므로 이후 관리자가 수정한 설명을 덮어쓰지 않습니다.
한 문장으로 실행되며 별도의 BEGIN·COMMIT은 필요하지 않습니다. DB 내용은 재배포 없이 상세 페이지에 반영됩니다.

홈·로그인·관리자·카트·주문·완료 화면을 실제 Tomcat에서 확인했고,
390px 모바일, 1024px 중간 화면, 1280px 데스크톱 너비에서 표시를 검증했습니다.
모바일 게임 관리 표는 표 영역 안에서만 가로 스크롤되며, 주문 관리 표는 세로 카드로 표시됩니다.
임시 테스트 계정으로 게임 등록→구매→주문 내역까지 검증했으며 테스트 데이터는 정리했습니다.
홈·게임 목록 미리보기는 `docs/previews/home-desktop.jpg`, `home-mobile.jpg`,
`browse-desktop.jpg`, `browse-mobile.jpg`에 저장했습니다.
분리한 홈·게임 목록은 390px, 768px, 1280px에서 가로 넘침 없이 표시되는 것을 확인했습니다.

## 동작과 코드 위치

- `JdbcUserRepository`: PreparedStatement로 계정 생성·조회. 사용자명은 소문자로 정규화하고 DB UNIQUE 제약으로 중복을 방지합니다.
- `PasswordHasher`: 계정별 무작위 salt와 PBKDF2-HMAC-SHA256 600,000회로 비밀번호를 저장합니다.
  평문 비밀번호나 해시는 세션에 보관하지 않습니다.
- `LoginServlet`, `RegisterServlet`, `LogoutServlet`: 입력 검증, 오류 표시, 세션 로그인 및 POST 로그아웃.
- `AuthFilter`: 카트 조회·추가·삭제 및 구매·주문 페이지 로그인 확인, 모든 POST 폼의 CSRF 토큰 확인, UTF-8 요청 처리.
- `AuthSession`: 로그인 시 세션 ID와 CSRF 토큰 갱신, 30분 미사용 만료, 로그인 후 요청했던 카트·상품 페이지로 복귀.
- `WEB-INF/views/`: 직접 URL로 열 수 없는 로그인·회원가입 JSP.
- `WEB-INF/jspf/header.jspf`: 전체 화면에서 공유하는 로그인 메뉴.
- `OrderRepository`: 주문 저장·확인 번호별 저장 및 조회·회원별 조회에 필요한 메서드를 정의하는 인터페이스.
- `JdbcOrderRepository`: 주문과 상세 항목을 하나의 트랜잭션으로 저장하고, 회원 ID로 제한하여 조회.
- `AppContextListener`: 애플리케이션에서 사용하는 주문 저장소를 JDBC 구현으로 연결.
- `AdminGameServlet`: 관리자 전용 게임 목록과 신규 등록. 준비된 로컬 이미지에서 표지를 선택합니다.
- `AdminGameServlet`의 `/admin/games/edit`: 제목·가격·장르·표지·설명과 개발사·출시일·지원 언어·갤러리를 수정합니다.
- `GameDetails`, `JdbcGameDetailsRepository`: 선택 상세 정보와 최대 6장의 갤러리 이미지를 순서대로 조회·저장합니다. 등록·수정은 기본 게임 정보와 같은 트랜잭션을 사용합니다.
- `AdminGameStatusServlet`: 관리자 전용 POST 판매 중지·재개. 명시한 상태를 저장하며 GET으로 변경하지 않습니다.
- `AdminGameDescriptionServlet`: 관리자 전용 기존 게임 설명 편집. 서버에서 5,000자 제한을 검증하며 기존 인증·CSRF 검사를 적용합니다.
- `AdminOrderServlet`, `JdbcAdminOrderRepository`: 관리자 전용 전체 주문 검색·집계·페이지 조회와 상세 보기. 회원용 주문 조회와 분리합니다.
- `AdminDashboardServlet`, `JdbcDashboardRepository`, `AdminDashboard`: 관리자 전용 완료 주문 요약·상태별 금액·일별 그래프·게임별 판매 현황. 읽기 전용이며 현재 DB 관리자 권한을 매 요청마다 검사합니다.
- `AccountServlet`, `JdbcAccountRepository`: 로그인한 회원의 마이페이지와 비밀번호 변경. 보유 게임·주문·찜의 전체 개수와 최근 주문·찜 3건씩을 같은 읽기 스냅샷으로 조회합니다.
- `LibraryServlet`, `JdbcLibraryRepository`, `LibraryPage`: 본인의 완료 주문에서 중복 없는 보유 게임을 조회하고 제목·장르 검색과 9개씩 페이지 표시를 제공합니다.
- `JdbcOwnershipRepository`, `OwnershipView`: 완료 주문에서 회원별 보유 게임 ID를 조회하며 쇼핑 화면의 보유 표시와 카트·주문 진입 차단에 사용합니다.
- `OrderActionServlet`, `OrderStatus`: 본인 결제 대기 주문의 테스트 결제·취소와 상태 표시. 실제 결제 서비스는 호출하지 않습니다.
- `ReviewServlet`, `JdbcReviewRepository`, `ReviewView`: 완료 주문이 있는 회원의 리뷰 작성·수정·삭제, 공개 별점·리뷰 목록, 내 리뷰 관리.
- `HomeServlet`, `JdbcHomeRepository`, `HomePage`, `HomeGame`: 최근 등록 배너와 신착·완료 구매자 순·평점 순의 최대 4개씩 및 실제 판매 중 개수. 이전 검색 URL은 목록으로 이동합니다.
- `BrowseServlet`: 공개 게임 목록, 제목·장르 검색과 장르 필터, 가격·제목·추가순 정렬 및 9개씩 페이지 표시.
- `JdbcGameRepository.findPage`, `CatalogPage`: DB 조건 검색·안정적인 정렬·LIMIT/OFFSET과 페이지 메타데이터.
- `CheckoutTokens`: 회원·카트 버전·확인한 가격에 묶인 주문 확인 번호 발급. 카트 변경 시 이전 확인 번호를 무효화합니다.
- `WishlistServlet`, `JdbcWishlistRepository`, `WishlistView`: 회원별 찜 저장·삭제·9개씩 목록 표시 및 카드·상세 하트 상태.

## 홈의 신작·인기작·고평점 섹션

상단 Hero는 신착 상위 3개·인기 상위 3개를 번갈아 묶은 최대 6개의 게임을 슬라이드로 소개합니다.
같은 게임은 한 번만 표시하고 두 조건에 모두 해당하면 `新着 & 人気`로 표시합니다.
표지·제목·장르·현재 가격과 실제 구매자 수를 같은 홈 조회 결과에서 가져옵니다. 로컬 검증 시에는 5개가 표시됐습니다.
약 6초마다 자동 전환하며 이전·다음·직접 선택·일시정지/재생 버튼을 제공합니다.
마우스를 올렸을 때·브라우저가 숨겨졌을 때·Hero가 화면 밖에 있을 때는 자동 전환을 쉬고,
키보드 포커스 또는 수동 선택 후에는 명시적으로 재생할 때까지 멈춥니다.
페이지 진입·뒤로 가기로 복귀할 때는 항상 재생 상태로 시작합니다.
동작 줄이기 설정에서도 자동 전환하되 이미지 전환 애니메이션은 생략합니다. 모바일 터치를 마우스 올림으로 취급하지 않습니다.
조작 버튼에서는 좌우 화살표·Home·End 키를 사용하고, 표시 중인 게임을 누르면 해당 상세 페이지로 이동합니다.
게임이 하나뿐이거나 JavaScript를 사용할 수 없으면 첫 번째 게임을 정적으로 표시하며 불필요한 버튼은 숨깁니다.
보유 표시·판매 중 게임 제한을 유지하며 추가 SQL과 관리자 설정은 필요하지 않습니다.
실제 Tomcat에서 자동 전환·첫/끝 순환·직접 선택·키보드·게임 상세 이동을 확인했고,
319·390·600·768·1280px에서 가로 넘침과 버튼 겹침을 검사했습니다.
화면 예시는 `docs/previews/home-hero-carousel-desktop.jpg`, `home-hero-carousel-mobile.jpg`입니다.
`新しく並んだゲーム`는 게임 ID 내림차순으로 최대 4개를 표시합니다. 현재 스토어의 자동 등록 순서를 기준으로 하며
별도 출시일 순서나 오늘 출시한 게임이라는 의미는 아닙니다.
기존 `#picks` 주소를 유지하고 홈 안에서 신착·인기·고평점으로 이동하는 링크를 제공합니다.

`みんなが選んだゲーム`는 전체 기간의 `COMPLETED` 주문에 포함된 고유 회원 수가 많은 순서입니다.
같은 회원의 과거 중복 구매와 같은 주문 안의 중복 항목도 한 명으로 세며, 결제 대기·취소 주문은 제외합니다.
같은 구매자 수에서는 게임 ID가 큰 순서이며 구매자가 0명인 게임을 대신 끼워 넣지 않습니다.
카드에 실제 구매자 수를 표시하고 회원 이름·ID·주문 정보는 노출하지 않습니다.

`感想から見つける、お気に入り`는 리뷰가 1개 이상인 게임의 평균 별점 내림차순입니다.
평균이 같으면 리뷰 수가 많은 순서, 다시 같으면 게임 ID 내림차순입니다.
순위는 반올림하기 전 평균을 사용하고 화면에는 소수점 한 자리 평균과 리뷰 개수를 함께 표시합니다.
최소 별점이나 최소 리뷰 3개 등의 추가 제한은 없으며 리뷰가 없는 게임은 넣지 않습니다.

세 섹션과 전체 판매 중 개수는 하나의 PostgreSQL SELECT에서 집계하여 동일한 시점의 데이터를 사용합니다.
구매자와 리뷰는 각각 먼저 집계하므로 리뷰와 주문 항목의 JOIN으로 숫자가 부풀지 않습니다.
DB에서 순위를 계산하고 최대 12개 행만 가져옵니다. 같은 게임은 여러 섹션에 나타날 수 있습니다.
판매 중지 게임은 모든 섹션과 배너·판매 중 개수에서 제외하며, 재개하면 보존된 통계로 다시 나타납니다.
새 주문 완료·리뷰 작성·수정·삭제는 다음 홈 조회에 반영됩니다. 홈은 no-store이며 별도 통계 캐시는 없습니다.
완료 주문이나 리뷰가 없으면 해당 섹션에 안내를 표시합니다. DB 오류는 503 재시도 화면으로 구분합니다.

모든 카드는 기존 게임 상세·찜 버튼·보유 게임 표시와 현재 가격을 사용합니다.
데스크톱은 4열, 1100px 이하에서는 2열로 표시하며 모바일 제목과 섹션 링크는 줄바꿈합니다.
기존 `/home?q=...&genre=...&sort=...` 주소는 조건을 보존하여 게임 목록으로 이동합니다.
추가 테이블·SQL·샘플 구매·샘플 리뷰는 필요하지 않으며 기존 데이터를 수정하지 않습니다.

전체 자동 테스트 267개와 홈·게임 목록·찜 JSP 컴파일이 통과했습니다.
실제 Tomcat에서 독립적인 SQL 집계와 화면의 게임 순서·구매자 수·평균 별점·리뷰 수·전체 개수를 비교했습니다.
브라우저에서 데스크톱·390px 모바일·768px 태블릿 배치, 세 섹션 링크와 카드의 게임 상세 이동을 확인했습니다.
검증은 읽기 전용으로 진행했으며 실제 리뷰·주문 데이터를 사용했습니다.

## 주문 중복 방지와 찜 목록

주문 확인 화면(`/checkout`)에서 서버가 발급한 `checkoutToken`을 숨김 필드로 보냅니다.
같은 카트를 여러 탭에서 확인하거나 새로고침하면 같은 확인 번호를 사용합니다.
`orders.checkout_token UUID`와 `(user_id, checkout_token)` 고유 인덱스로 DB에서도 중복을 막습니다.
동시에 같은 번호가 제출되면 주문과 상세 항목은 한 번만 저장하고 같은 완료 주소를 반환합니다.
저장 후 응답이 끊긴 경우에도 확인 번호로 저장된 주문을 찾아 안내합니다.
기존 주문의 확인 번호는 NULL로 유지되며 구매 이력은 바뀌지 않습니다.

카트를 추가·삭제한 뒤 오래된 확인 화면을 제출하면 새로 확인하도록 안내합니다.
가격이 바뀌면 새 금액과 새 확인 번호로 재확정을 요구합니다.
완료된 주문을 다시 제출해도 그 사이 새로 담은 카트는 지우지 않습니다.
처리 중에는 버튼도 비활성화하지만, 실제 중복 방지는 서버와 DB가 수행합니다.
CSRF 토큰과 주문 확인 번호는 서로 다른 역할이며 주문에는 둘 다 필요합니다.

찜 목록은 `/gamestore/wishlist`와 상단 `お気に入り` 메뉴에서 엽니다.
홈 추천 카드·전체 게임 카드·상세 페이지의 하트로 추가하고 다시 누르면 삭제합니다.
`wishlist_items`의 기본키 `(user_id, game_id)`로 같은 게임을 여러 번 저장하지 않습니다.
추가·삭제는 POST와 CSRF 검사를 사용하며 요청의 userId 값은 사용하지 않습니다.
모든 조회·삭제 조건은 로그인 세션의 회원 ID를 사용합니다.
로그아웃 후 다시 로그인해도 찜이 유지되고, 판매 중지된 게임도 표시와 삭제가 가능합니다.
찜 목록은 최근 추가 순으로 9개씩 표시합니다. 중복 추가는 최초 저장 시각을 바꾸지 않습니다.

하트는 `js/wishlist.js`의 `fetch`로 화면 전체를 새로고침하지 않고 저장·삭제합니다.
누르는 즉시 상태를 표시하고, 홈의 여러 섹션에 같은 게임이 있으면 하트를 함께 바꿉니다.
처리 중 중복 클릭을 막으며 실패하면 이전 표시로 돌아갑니다. 로그인 만료(401)·CSRF 만료(403)는
자동 이동 대신 복구 링크를 표시합니다. 네트워크 오류·15초 시간 초과는 저장 결과를 확인할 수 없다고 안내합니다.
성공 알림은 4초 후 사라지고 오류 안내는 직접 닫을 수 있습니다.
찜 목록에서는 서버에서 다시 읽은 목록 영역만 교체하여 개수·페이지·빈 목록을 갱신합니다.
마지막 페이지의 항목을 모두 삭제하면 앞 페이지로 보정하며 전체 페이지를 이동하지 않습니다.
저장은 성공했지만 목록 조회가 실패한 경우 저장 상태를 되돌리지 않고 목록 재조회 링크를 표시합니다.
JavaScript를 사용할 수 없는 환경에서는 기존 POST 폼과 안전한 복귀 주소를 그대로 사용합니다.
추가 DB 마이그레이션은 없습니다.
비회원은 로그인으로 이동하며 로그인 전의 추가·삭제 요청은 자동으로 실행하지 않습니다.
하트를 누른 뒤에는 허용된 사이트 내부 주소로만 돌아가며 검색·장르·정렬·페이지 조건을 유지합니다.

DB 적용·확인은 다음 도구로도 가능합니다. 현재 로컬 DB에는 이미 적용했습니다.

```powershell
java -cp "target/classes;target/gamestore/WEB-INF/lib/*" scripts/MemberFeaturesDatabaseSetup.java --check
```

새 환경에 014·015만 적용하려면 `--apply`를 사용합니다.
화면 예시는 `docs/previews/wishlist-desktop.jpg`, `wishlist-mobile.jpg`, `checkout-confirmation.jpg`에 저장했습니다.

## 관리자 지정과 게임 등록

1. 웹에서 사용할 계정을 일반 회원으로 가입합니다.
2. DB 클라이언트(pgAdmin 등)에서 `sql/009_promote_admin.sql`을 엽니다.
3. `target_username TEXT := 'CHANGE_ME';`의 CHANGE_ME를 가입한 아이디로 바꾼 뒤 실행합니다.
   잘못된 기본값 그대로 실행하거나 없는 계정을 지정하면 오류로 중단됩니다.
4. 로그아웃 후 다시 로그인하면 상단에 **ゲーム管理** 메뉴가 표시됩니다.
   주소는 `/gamestore/admin/games`입니다.
5. 제목(최대 200자), 정수 가격(0 이상), 장르(최대 50자), 이미지를 선택하고
   선택 입력인 설명(최대 5,000자)을 작성해 등록합니다.
   게임 ID는 자동 생성되며 등록 즉시 홈페이지·상세·장바구니·주문에 사용할 수 있습니다.
6. 기존 게임의 설명은 목록의 `説明を編集`에서 작성한 뒤 `説明を保存`으로 저장합니다.
   `詳細ページを確認`으로 실제 표시를 확인할 수 있습니다.
7. 제목·가격·장르·표지까지 수정하려면 `情報を編集`을 누르고 `変更を保存`으로 저장합니다.
8. `販売を休止`를 누르면 홈·게임 목록에서 숨기고 구매를 차단합니다.
   다시 `販売を再開`를 누르면 같은 게임 ID로 판매를 재개합니다.

판매 상태는 `games.is_active BOOLEAN NOT NULL DEFAULT TRUE`에 저장합니다.
중지한 게임도 직접 상세 주소에서는 판매 휴지 안내와 설명을 볼 수 있습니다.
카트 조회·주문 확인은 DB의 최신 가격과 판매 상태를 반영합니다.
기존 카트의 판매 중지 상품은 표시를 유지하여 사용자가 삭제할 수 있고 구매 진행은 막습니다.
주문 확정 전에 가격이 바뀌면 409 응답으로 새 금액을 보여주고 재확정을 요구합니다.
주문 저장 트랜잭션에서도 게임 행을 ID 순서로 FOR SHARE 잠근 뒤 가격·판매 상태를 재검사합니다.
관리자의 변경과 주문 확정이 겹쳐도 변경된 상태를 무시한 새 주문은 저장하지 않습니다.
판매 중지는 행을 삭제하지 않아 과거 주문이 유지되며 구매 당시 가격은 order_items에 보존됩니다.
과거 주문의 제목·장르·표지는 현재 게임 정보를 표시하고, 금액은 구매 당시 값을 표시합니다.

모든 회원가입은 USER 권한으로 저장됩니다. 웹에는 관리자 생성·권한 변경 기능이 없습니다.
관리자 URL은 요청할 때마다 DB 권한을 다시 검사합니다.
SQL로 `UPDATE users SET role = 'USER' WHERE username = '대상아이디';`를 실행하면 기존 관리자 세션도 접근이 차단됩니다.
이 방식에서 권한 변경을 수행하는 주체는 DB에 접속하는 운영자입니다.
애플리케이션 DB 계정의 비밀번호와 DB 접속 권한은 운영자가 관리해야 합니다.

새 이미지 파일은 소스의 images 폴더에 넣고 재배포하면 목록에 표시됩니다.
게임 정보 수정과 판매 중지·재개는 관리자 목록에서 사용할 수 있습니다. 표지는 준비된 로컬 이미지에서 선택합니다.

DB 구조와 샘플 데이터 확인(프로젝트 폴더에서 빌드 후 실행):

```powershell
java -cp "target/classes;target/gamestore/WEB-INF/lib/*" scripts/CatalogDatabaseSetup.java --check
```

`--apply`는 008·010·012·014·015·016·017·018·019·020 SQL을 실행하며, 실제 계정의 관리자 승격은 하지 않습니다.

`scripts/SaleStatusDatabaseSetup.java --check` 또는 `--apply`를 실행할 수 있습니다.

사용자명은 영문·숫자·밑줄 4~30자, 비밀번호는 8~128자입니다.
회원가입 후 로그인 화면으로 이동하고, 로그인 성공 시 홈 또는 요청했던 구매·주문목록 화면으로 이동합니다.
로그아웃하면 세션과 장바구니를 비웁니다.
게임 탐색·상세는 비회원도 이용할 수 있지만 카트는 회원 전용입니다.
`/cart`, `/cart/remove`, `/cart.jsp`는 서버 필터에서 로그인 여부를 검사합니다.
비회원이 카트 메뉴를 누르면 로그인 후 카트로, 상품 담기를 누르면 로그인 후 해당 상품 상세로 돌아갑니다.
로그인 전의 담기·삭제 요청은 실행하지 않으며, 로그인 후 상품 상세에서 다시 담기를 눌러야 합니다.

## 게임 상세 정보와 이미지 갤러리

게임 상세에 개발사·출시일·지원 언어를 표시합니다. 선택 항목이 비어 있으면 `未登録`로 표시하며,
이미지가 없는 게임은 갤러리 영역을 생략하고 기존 표지·설명·구매·리뷰 기능을 유지합니다.
이미지는 최대 6장까지 저장한 순서대로 표시합니다. 썸네일 클릭, 좌우 방향키, Home/End로 선택할 수 있고
현재 위치를 화면과 보조 기술에 알립니다. `画像を別タブで開く`는 현재 선택한 원본을 엽니다.
JavaScript가 없어도 각 썸네일 링크로 원본을 열 수 있습니다.

관리자 등록·정보 수정 화면의 `ゲームの詳しい情報`와 `ギャラリー画像`에서 입력합니다.
개발사는 100자, 지원 언어·이미지 보충 설명은 각각 200자이며 출시일은 비워두거나 1000~9999년의 유효한 날짜를 사용합니다.
이미지 1~6의 번호 순서로 표시하며 빈 칸은 건너뜁니다. 중복 이미지·없는 파일·외부 주소·상위 경로는 서버에서 거부합니다.
갤러리는 `src/main/webapp/images/screenshots/`의 소문자 파일명 PNG/JPG/JPEG/WebP만 선택할 수 있습니다.
새 파일을 해당 폴더에 추가하고 재배포하면 선택 목록에 나타납니다. 파일 업로드 기능은 포함하지 않습니다.
표지는 기존 `images/` 폴더의 목록을 계속 사용하며 갤러리와 별도로 선택합니다.

이미지 선택 시 미리보기가 나타납니다. 불필요한 칸은 `画像なし`로 바꾸고 저장하면 됩니다.
기존 이미지 파일이 사라진 경우에는 해당 선택을 유지하면서 누락 안내를 표시하여 무심코 삭제하지 않도록 합니다.
오래된 편집 폼에서 새 항목이 누락되면 400으로 차단하고 새 편집 화면을 열도록 안내합니다.
잘못된 입력·DB 저장 오류 때 입력값과 선택 순서를 유지합니다. 조회 오류는 빈 정보처럼 처리하지 않고 503을 표시합니다.
기본 게임 정보·상세 정보·갤러리 교체는 한 트랜잭션이므로 중간 실패 시 전부 되돌립니다.
정보 수정으로 판매가 재개되지 않으며 설명만 수정해도 상세 정보·갤러리는 보존됩니다.
게임 상세의 텍스트·보충 설명·제목은 HTML 이스케이프하여 표시합니다.

`game_details`는 게임당 선택 정보 한 건, `game_screenshots`는 1~6번 위치와 이미지 경로를 보관합니다.
DB에도 날짜·문자 길이·로컬 이미지 경로·위치·중복 제약을 적용했습니다.
018·019는 각각 단일 DO 문장이며 관리자 편집 내용을 반복 실행으로 덮어쓰지 않습니다.
019는 아직 상세 정보가 없는 첫 번째 Moonlit 샘플에만 가상의 개발사·출시일·언어와 이미지 2장을 추가합니다.
이미지를 의도적으로 비운 뒤 다시 실행해도 복구하거나 다른 게임에 추가하지 않습니다.

020은 현재 샘플 12개의 개발사·출시일·지원 언어 중 비어 있는 값만 채웁니다.
모든 값은 가상 게임용 샘플이며 개발사에 `架空` 표시를 붙였습니다. 기존의 비어 있지 않은 값은 보존합니다.
현재 제목을 바꿔도 표지 경로로 대응하며 다른 표지의 새 게임에는 임의로 정보를 넣지 않습니다.
이미지·갤러리 순서·보충 설명·게임 가격·계정·주문·찜·리뷰는 변경하지 않습니다.
같은 SQL을 다시 실행해도 중복하지 않지만 관리자가 이후 비운 필드는 다시 채울 수 있습니다.
메타데이터만 따로 적용하려면 다음 명령을 사용합니다. 현재 로컬 DB는 적용 완료하여 12개 모두 표시됩니다.

```powershell
java -cp "target/classes;target/gamestore/WEB-INF/lib/*" scripts/CatalogMetadataSetup.java --apply
```

이 스크립트는 관련 없는 테이블의 모든 행과 기존 입력값·갤러리 설명을 트랜잭션 안에서 비교하여 변경되면 롤백합니다.
`--check`는 전체 게임 수·세 항목이 모두 채워진 게임 수·갤러리 이미지 수를 조회합니다.

현재 로컬 DB에는 적용했습니다. 다른 환경에서 빌드 후 한 번에 적용하려면 다음 명령을 사용합니다.

```powershell
java -cp "target/classes;target/gamestore/WEB-INF/lib/*" scripts/GameDetailsDatabaseSetup.java --apply
```

`--check`는 상세 정보·이미지 개수만 조회합니다. 수동으로 적용한다면 A5에서 018, 019, 020 순서대로 실행하면 되며
별도의 BEGIN/COMMIT을 덧붙일 필요는 없습니다.

Moonlit의 갤러리는 실제 플레이 화면이 아닌 가상 게임용 AI 생성 일러스트이며, 화면에도 그 사실을 표시합니다.
이미지는 `images/screenshots/moonlit-farm.png`, `moonlit-night.png`이고 내장 image_gen 도구로 제작했습니다.
최종 생성 프롬프트와 용도는 `docs/gallery-assets.md`에 기록했습니다.
미리보기는 `docs/previews/game-gallery-desktop.jpg`, `game-gallery-mobile.jpg`, `game-gallery-section-desktop.jpg`입니다.

실제 Tomcat에서 공개 상세 정보·일본어/한국어/영어·HTML 문자·이미지 응답·갤러리 순서 변경/비우기·판매 중지 상태 유지를 확인했습니다.
브라우저에서 썸네일·방향키 전환과 390px 모바일 배치를 확인했습니다.
임시 게임을 정리한 뒤 기존 8개 테이블의 모든 행이 검증 전과 같고 의도한 Moonlit 샘플만 남았는지 비교했습니다.
관리자 저장·입력 검증·오류 처리는 자동 테스트로 확인했고, 실제 Tomcat의 Jasper로 등록·편집·상세 JSP를 컴파일하여 오류가 없음을 확인했습니다.
이번 검증에서는 새 관리자 권한을 부여하지 않았으며 관리자 계정의 실제 브라우저 등록·편집 동작은 수행하지 않았습니다.

## 마이페이지와 비밀번호 변경

상단 `マイページ` 또는 `/gamestore/account`에서 본인 사용자명·가입일·보유 게임 수·찜 수와
최근 주문 3건·최근 찜 3개를 확인하고 전체 목록·상세로 이동할 수 있습니다.
주문은 주문 시각·주문번호 내림차순, 찜은 저장 시각·게임 ID 내림차순으로 조회합니다.
본인 데이터는 세션의 회원 ID로만 조회하며 URL의 userId는 사용하지 않습니다.
주문에는 구매 당시 총액을, 찜에는 현재 게임 정보를 표시하며 판매 중지 게임도 찜에 남습니다.
주문·찜이 없는 새 회원에게는 게임을 찾아볼 수 있는 안내를 표시합니다.
DB 오류는 503 안내를 표시하고 주문·찜이 0건인 것처럼 처리하지 않습니다.
상단 메뉴는 홈·게임 목록·라이브러리·마이페이지로 정리했고 관리자에게는 관리 메뉴를 추가로 표시합니다.
주문·찜의 직접 링크는 마이페이지와 하단 메뉴에서도 이용할 수 있습니다.

`/gamestore/account/password`에서 현재 비밀번호·새 비밀번호·새 비밀번호 확인을 입력합니다.
8~128자, 확인 일치, 기존 비밀번호와 다른 값인지 서버에서 검증합니다. 비밀번호는 trim하지 않습니다.
현재 비밀번호를 검증한 뒤 PBKDF2의 새 salt로 저장하며 회원 ID와 기존 해시가 모두 일치할 때만 갱신해
동시 변경 시 덮어쓰기를 방지합니다. 다른 회원 ID를 폼으로 보내도 로그인한 본인만 대상이 됩니다.
POST에는 CSRF 검사를 적용하고 입력한 비밀번호를 화면·세션에 복사하지 않습니다.
성공 후 이 브라우저의 세션 ID·CSRF를 새로 발급하고 카트와 로그인 상태를 유지합니다.
변경된 비밀번호는 다음 로그인부터 사용하며 다른 기기의 기존 로그인 세션을 강제로 종료하는 기능은 포함하지 않습니다.
DB 통신 오류로 성공 여부를 확인하지 못하면 새 비밀번호로 로그인 가능한지 확인하도록 안내합니다.
기존 테이블만 사용하므로 마이페이지용 추가 SQL은 없습니다.

미리보기는 임시 테스트 계정으로 촬영한 `docs/previews/account-desktop.jpg`, `account-mobile.jpg`,
`account-empty-desktop.jpg`, `account-password-desktop.jpg`, `account-password-mobile.jpg`입니다.
390px·768px·데스크톱에서 가로 넘침 없이 표시되며 최근 내역에서 상세와 전체 목록으로 이동하는 것을 확인했습니다.
실제 Tomcat에서 회원 분리·빈 상태·로그인 후 복귀·비밀번호 변경 검증·CSRF와 세션 갱신·카트 유지,
기존 비밀번호 로그인 실패·새 비밀번호 로그인 성공을 확인했습니다.
검증용 회원 2명·주문 5건·찜 5개는 정리했고 기존 계정·주문·주문 항목·찜 개수를 보존했습니다.

## 주문에서 이어지는 내 라이브러리

상단 `ライブラリ` 또는 `/gamestore/library`에서 본인의 완료 주문에 포함된 게임을 모아 봅니다.
`COMPLETED`만 보유 게임으로 계산하고 결제 대기·취소 주문은 제외합니다.
과거에 같은 게임을 여러 번 구매한 기록도 한 번만 표시하며, 최초 결제 완료 시각·게임 ID 내림차순으로 정렬합니다.
기존 주문·주문 항목·게임·리뷰 테이블을 사용하므로 추가 SQL은 없습니다.

게임 카드에는 현재 표지·제목·장르와 최초 취득일을 표시합니다. 판매 중지된 보유 게임도 남습니다.
`ゲーム情報を見る`에서 상세 설명으로, `レビューを書く`에서 상세의 리뷰 영역으로 이동합니다.
이미 작성했다면 본인 별점·작성 완료 표시와 `レビューを見る・編集` 링크를 제공합니다.
리뷰 작성·수정은 기존 서버의 완료 주문·작성자 검사와 CSRF 검사를 그대로 사용합니다.

제목·장르를 검색할 수 있고 한 페이지에 9개를 표시합니다. 검색어는 앞뒤 공백 제거 후 최대 100자이며
SQL 특수 문자를 와일드카드로 취급하지 않습니다. 개수·페이지·본인 별점은 같은 읽기 스냅샷으로 조회합니다.
회원 ID는 로그인 세션에서만 가져오며 URL의 userId는 사용하지 않습니다.
비회원은 로그인 후 라이브러리로 돌아옵니다. DB 조회 실패는 503 안내로 구분합니다.

라이브러리와 주문 이력은 탭으로 오갈 수 있습니다. 주문 상세의 게임 제목도 상세 정보로 연결하며,
완료 주문에는 라이브러리·리뷰 링크를 표시합니다. 마이페이지 첫 카드도 보유 게임 수와 라이브러리로 연결합니다.
주문 금액·상태·결제 대기는 기존 주문 이력에서 계속 확인할 수 있습니다.

미리보기는 임시 테스트 계정으로 촬영한 `docs/previews/library-desktop.jpg`,
`library-search-desktop.jpg`, `library-mobile.jpg`입니다.
실제 Tomcat에서 회원 분리·중복 구매·검색·페이지 이동·본인 별점·로그인 후 복귀와
대기 주문 결제 후 즉시 추가를 확인했습니다. 브라우저에서 라이브러리 → 상세 → 리뷰 작성·편집도 확인했습니다.
검증용 회원 3명·주문 5건·리뷰 2개는 정리했고 기존 계정·주문·항목·찜·리뷰 개수를 보존했습니다.

## 보유 게임 재구매 방지

디지털 게임은 본인 `COMPLETED` 주문에 포함되면 보유한 것으로 처리합니다.
결제 대기·취소 주문과 다른 회원의 구매는 보유 판정에 포함하지 않습니다.
게임 상세의 구매 버튼은 `ライブラリで見る`로 바뀌고 홈 추천·게임 목록·찜에도 보유 표시가 나타납니다.

인증·CSRF 검사 후 쇼핑 경로에서 로그인 세션의 회원 ID로 보유 목록을 읽습니다.

다른 창에서 먼저 구매해 오래된 카트에 보유 게임이 남았다면 항목과 삭제 버튼을 보여주고 구매 진행은 막습니다.
오래된 주문 확인 화면의 제출도 409이며, 카트에서 해당 항목을 삭제하고 다시 확인해야 합니다.

최종 검사는 주문 저장·결제 완료 트랜잭션 안에서 다시 수행합니다.
회원 행을 먼저 `FOR UPDATE`로 잠그고 READ COMMITTED로 보유 여부를 확인하여 같은 회원의 주문 생성·상태 변경을 순서대로 처리합니다.
서로 다른 세션·서로 다른 주문번호로 같은 게임을 동시에 결제해도 한 주문만 완료됩니다.
한 항목이라도 이미 보유했다면 해당 대기 주문 전체의 결제를 409로 차단하고 상태·항목·금액을 유지합니다.
주문 상세는 라이브러리와 취소를 안내합니다. 취소한 뒤 미구매 게임만 새 주문에 넣을 수 있습니다.
서로 다른 게임의 주문이나 다른 회원의 구매는 허용합니다. 한 주문 안의 중복 게임 항목도 저장하지 않습니다.

새 주문이나 완료 시각을 만들지 않습니다. 과거 중복 주문과 라이브러리·리뷰·가격 기록은 수정하지 않습니다.
추가 테이블이나 SQL 마이그레이션은 없습니다.

## 주문 상태·테스트 결제·취소

현재 결제는 학습용 테스트입니다. 카드 정보를 받거나 실제 금액을 청구하지 않습니다.
새 주문은 `PENDING`(支払い待ち)으로 저장하고 기존 `/order/complete?id=주문번호`에서
테스트 결제 완료 또는 주문 취소를 선택합니다. 이 주소는 세 상태 모두의 주문 상세로 계속 사용합니다.
정상 주문 저장 후 카트는 비우며 취소 시 상품을 카트에 자동으로 되돌리지 않습니다.
결제 대기 주문의 가격은 주문 저장 당시 금액을 사용합니다.
나중에 상품 가격·판매 상태가 바뀌어도 이미 저장된 결제 대기 주문의 금액은 바뀌지 않습니다.

- `PENDING → COMPLETED`: 테스트 결제 완료. 완료 시각을 기록합니다.
- `PENDING → CANCELLED`: 취소 확인을 펼친 뒤 확정. 취소 시각을 기록하며 주문·항목·금액은 남깁니다.
- 완료 후 취소, 취소 후 완료는 409로 차단하고 현재 상태를 표시합니다. 같은 동작을 반복하면 같은 상태로 성공 처리하며 시각을 다시 쓰지 않습니다.

두 변경 모두 회원 로그인과 POST·CSRF가 필요하며 로그인한 본인 ID와 주문 ID를 조건으로 사용합니다.
다른 회원 주문과 없는 주문은 모두 404이고 GET 요청으로 상태를 변경하지 않습니다.
DB의 조건부 UPDATE가 동시 요청 중 하나의 상태 변경만 허용합니다.
기존 확인 번호로 완료·취소 주문을 재제출해도 새 주문을 만들거나 상태를 되돌리지 않고 새 카트도 보존합니다.
서버에서 상태를 결정하므로 폼으로 보낸 status·userId·금액을 신뢰하지 않습니다.
결과를 확인하지 못한 통신 오류에는 503 안내와 주문 이력 링크를 표시합니다.

`sql/016_order_status.sql`은 한 개의 원자적 DO 문장입니다. 기존 주문은 `COMPLETED`로 유지하고
완료 시각을 기존 주문 시각으로 채운 뒤 새 주문 기본값을 `PENDING`으로 바꿉니다.
DB CHECK는 상태값과 완료·취소 시각의 조합을 검증합니다. 반복 적용해도 이미 변경된 상태를 초기화하지 않습니다.
현재 로컬 DB에는 적용했습니다. 다른 환경에서는 빌드 후 다음 명령을 사용합니다.


이 스크립트는 적용 전후 주문의 원래 필드와 항목을 비교한 뒤 커밋합니다. `--check`는 상태별 개수만 조회합니다.
마이페이지·회원 주문 목록·관리자 목록·상세에서 같은 상태를 표시합니다.
관리자 상태 필터는 검색어·날짜와 함께 사용하고 상세에서 복귀하거나 페이지를 옮겨도 유지됩니다.

## 관리자 운영 대시보드

관리자 메뉴의 `ダッシュボード` 또는 `/gamestore/admin/dashboard`에서 확인합니다.
`/gamestore/admin`도 대시보드로 이동하며 비회원은 로그인 후 대시보드로 돌아옵니다.
일반 회원·권한이 해제된 기존 관리자·삭제 계정은 403, 권한 확인 DB 오류는 503으로 차단합니다.
페이지와 조회는 GET만 제공하며 새 관리자 계정이나 권한을 만들지 않습니다.

기본값은 전체 기간이며 `注文受付日・開始/終了`와 `直近30日を見る`로 기간을 좁힐 수 있습니다.
시작일과 종료일의 하루 전체를 포함합니다. 모든 집계는 **주문 접수일(created_at)** 기준이며,
그 기간에 접수된 주문의 **현재 상태**를 계산합니다. 결제 완료일로 집계하는 회계용 매출 보고서는 아닙니다.
날짜 형식·유효성·시작/종료 순서는 서버에서 검사하며 오류 때 400 안내와 입력값을 유지합니다.

요약 카드는 완료 주문 금액·완료 주문 건수·판매 게임 본수·고유 구매 회원 수를 표시합니다.
완료 금액은 `COMPLETED` 주문의 구매 당시 주문 총액만 더하므로 대기·취소 주문을 포함하지 않습니다.
판매 본수는 완료 주문의 상품 항목 수로 세고 같은 회원의 과거 반복 구매도 실제 기록대로 포함합니다.
구매 회원 수는 같은 회원을 한 명으로 셉니다. 무료 주문은 금액이 0원이어도 완료 주문·판매 본수에 포함합니다.
금액·건수는 long으로 처리하여 여러 주문의 합계가 INTEGER 범위를 넘어도 유지합니다.
실제 입금이 없는 테스트 결제의 집계임을 화면에 표시합니다.

상태 카드에는 대기·완료·취소 각각의 건수와 금액을 분리합니다.
누르면 같은 기간·상태의 기존 주문 관리 목록으로 이동합니다.
일별 그래프는 선택 기간의 끝을 기준으로 최대 최근 14일을 표시합니다. 종료일이 없으면 오늘까지를 표시하며,
미래의 시작일만 선택했다면 해당 시작일 하루를 표시합니다. 주문이 없는 날도 0원으로 채웁니다.
범위 전체 요약과 달리 그래프는 화면에 명시한 최대 14일 구간만 표시합니다.
막대는 최대 일별 금액을 기준으로 높이를 조절하며 `日別の件数・金額を表で見る`에서 정확한 숫자를 볼 수 있습니다.

게임별 표는 완료 상품 금액 내림차순·판매 본수 내림차순·게임 ID 내림차순입니다.
현재 판매 중지된 게임과 기간 내 판매가 없는 게임도 포함하며 10개씩 페이지를 나눕니다.
완료 상품 금액은 `order_items.price`의 구매 당시 단가를 더하며 현재 게임 가격으로 다시 계산하지 않습니다.

현재 제목·표지·판매 상태를 표시하고 게임 제목에서 관리자 정보 편집으로 이동합니다.
페이지를 바꿔도 기간을 유지하며 요약·그래프는 전체 기간 데이터 그대로입니다.

모든 집계와 페이지 조회는 읽기 전용 REPEATABLE READ 트랜잭션 한 개를 사용합니다.
조회 도중 결제가 완료돼도 요약·표·그래프가 서로 다른 시점의 숫자를 섞지 않습니다.

추가 테이블이나 SQL이 필요하지 않으며 기존 주문·게임·리뷰·권한을 변경하지 않습니다.

## 관리자 주문 관리

관리자로 로그인한 뒤 상단의 `注文管理` 또는 `/gamestore/admin/orders`를 엽니다.
주문자 사용자명·주문번호의 부분 검색과 시작일·종료일 필터를 함께 사용할 수 있습니다.
날짜는 DB에 저장된 주문 시각 기준이며 시작일 00:00부터 종료일 다음 날 00:00 직전까지 포함합니다.
잘못된 날짜·뒤집힌 범위·100자를 넘는 검색어는 400 오류와 안내를 표시하고 DB 조회를 실행하지 않습니다.
주문은 주문 시각·주문번호 내림차순으로 페이지당 10건씩 표시합니다.
상단 주문 수는 취소를 포함한 검색 결과 전체의 개수이고, 금액은 해당 결과에서 취소를 제외한 집계입니다. 실제 결제 매출 통계는 아닙니다.
집계와 목록은 같은 읽기 스냅샷을 사용하며 합계 금액은 64비트 정수로 처리합니다.
상세에는 주문자·회원 ID·주문 시각·게임·구매 당시 가격을 표시합니다.
게임 제목·표지·장르는 현재 카탈로그 정보를 사용하고 판매 중지 상품도 주문 상세에 남습니다.
상세에서 목록으로 돌아오면 검색어·날짜·페이지가 유지됩니다.
결과 없음과 DB 조회 실패를 구분하여, 실패를 주문 0건이나 금액 0원으로 표시하지 않습니다.

회원용 `/orders`, `/order/complete`는 계속 로그인한 본인의 주문만 조회합니다.
전체 주문 쿼리는 `JdbcAdminOrderRepository`에 분리했으며 `/admin/orders`와
`/admin/orders/detail`은 요청마다 DB의 현재 ADMIN 권한을 검사합니다.
로그인 중 권한을 해제해도 다음 요청부터 차단하며 웹에서 계정 승격은 할 수 없습니다.
주문 상태 기능과 함께 사용하려면 016 SQL을 배포 전에 적용합니다.
모바일에서는 주문 목록이 세로 카드로 바뀝니다.
미리보기는 `docs/previews/admin-orders-desktop.jpg`, `admin-orders-mobile.jpg`,
`admin-order-detail-desktop.jpg`, `admin-order-detail-mobile.jpg`이며 임시 테스트 데이터로 촬영했습니다.

SQL 권한 해제 후 기존 세션 차단을 확인했습니다. 해당 테스트 계정·게임·주문은 정리했습니다.
실제 PostgreSQL·Tomcat 환경에서는 다음 흐름도 확인하세요.

1. 가입 성공, 중복 사용자명, 확인 비밀번호 불일치.
2. 잘못된 비밀번호로 로그인 실패, 정상 로그인 후 사용자명 표시.
3. 비로그인 카트 접근 → 로그인 → 카트로 복귀. 비로그인 상품 담기 → 로그인 → 해당 상세로 복귀 → 다시 담기.
4. A 회원 주문 후 B 회원에게 주문 목록과 완료 URL이 노출되지 않는지 확인.
5. 로그아웃 후 주문목록 접근 시 로그인 화면으로 이동.
6. 주문한 뒤 Tomcat을 재시작하고 다시 로그인해 주문이 유지되는지 확인.

## 주문 DB 구조와 동작

`orders.user_id`는 `users.user_id`를 참조하며 NULL을 허용하지 않습니다.
`order_items.order_id`로 주문 상세를 연결하고, `order_items.price`에 구매 당시 가격을 보관합니다.
주문 생성 시 게임 가격을 DB에서 다시 조회합니다. 상품 가격이 이후 바뀌어도 주문 상세는 구매 가격을 표시합니다.
회원용 목록·검색·완료 조회는 모두 로그인한 회원 ID를 조건에 포함합니다.
주문과 상세 항목이 모두 저장된 후에만 장바구니를 비웁니다.
DB 오류가 발생하면 트랜잭션을 롤백하고, 장바구니와 오류 안내를 구매 화면에 표시합니다.
네트워크 오류로 완료 여부가 불확실한 경우 재시도 전에 주문 내역을 확인하세요.
주문은 서버 재시작·WAR 재배포 후에도 DB에 유지됩니다.
세션 장바구니는 서버 재시작 시 보존을 보장하지 않습니다.

DB 구조 확인은 빌드 후 다음 명령으로도 가능합니다(프로젝트 폴더에서 실행).

```powershell
java -cp "target/classes;target/gamestore/WEB-INF/lib/*" scripts/OrderDatabaseSetup.java --check
```

`--apply`를 지정하면 주문 테이블이 비어 있고 user_id가 없을 때만 007 SQL을 적용합니다.
기존에 작성하던 `src/main/java/com/JdbcOrderRepositoryTest.java`는 수동 연습 파일로 유지했습니다.
자동 DB 통합 테스트는 `src/test/java/com/gamestore/repository/JdbcOrderRepositoryTest.java`입니다.
